# C16: 97ns 최악 경로와 DATAFLOW 제거 후보 미채택

2026-11-06. 사용자 요청으로 현재 DATAFLOW 제거 방향을 미채택·보류로 정리하고 원인을 조사했다. 새 합성·P&R은 하지 않고 routed DCP를 읽어 DSP 속성과 입력 핀 포함 타이밍만 추가 추출했다.

## 결과와 판단

- 조건: 목표18ns, HLS uncertainty1ns, LOOP_T II2/Depth17. HLS 추정16.939ns.
- Vivado 합성 후 비교 주기93.405ns, routed97.116ns, WNS−79.116ns. 배선만의 악화가 아니며 RTL 합성 단계부터 긴 경로가 존재한다.
- 실제 최악 데이터 경로97.097ns = 논리70.170ns + 배선26.927ns. 논리 단계353.
- routed LUT23356/FF7574/DSP502/BRAM0. 원래 v2 최종본은15ns 제약, LUT41387/FF41088/DSP362, WNS+0.093ns. 구현 클록 조건이 다르며 자원 감소만으로 채택할 수 없다.
- 사용자 판단: 현재 DATAFLOW 제거 계열은 채택하지 않고 추가 튜닝 보류. 동일 계열의 모든 가능한 구현이 실패한다는 증명은 아니다. C17 결합 비트 축소는 별도 후보이며 이 결정에 포함하지 않는다.

## 실제 최악 경로는 GRU가 아니라 FEx

`timing100/setup_paths100.rpt`의 시작점은 `ap_CS_fsm_reg[1]_replica/C`, 끝점은 `select_ln72_3_reg_164419_reg[6]/D`이다. 분석한100개 모두 FSM 레지스터에서 시작하고, 동일한42×16/57×16 공유 곱셈기 쌍을 지난다. 끝점 레지스터군은 select_ln72_3 30개, select_ln73_3 42개, amp 28개다. 끝 핀은 D41/CE30/S27/R2개로 데이터뿐 아니라 제어 핀 경로도 포함한다.

소스는 원래 후보 `src/linear_layer.h:67`의 `inv_sqrt = inv_sqrt * (1.5 - 0.5*amp2*inv_sqrt*inv_sqrt)`와 :70~73의 amp/sin/cos 계산이다. 따라서 HLS II2 실패 경고에서 본 GRU tanh→상태 갱신→recurrent 경로와 이번 routed 최악 경로를 구분해야 한다.

## RTL 입력 연결과 레지스터 경계

대상 RTL: `prj/sol1/syn/verilog/ResGRU_ResGRU_Pipeline_LOOP_T.v`.

1. :28445의 `mul_42s_16s_56_1_1_U118` 입력은 grp_fu_6541_p0/p1이다. :35400~35425의 조합 mux는 pp0_stage0에서 mul_ln67_6_reg/inv_sqrt_4_reg, pp0_stage1에서 mul_ln67_9_reg/inv_sqrt_5_reg를 선택한다. 두 NR 단계가 같은 물리 곱셈기를 공유한다.
2. U118 출력 grp_fu_6541_p2는 :63543/:63553에서 부호 확장되고 :65445/:65447의 `상수 - 곱`에 들어간다. :35456~35481 mux가 이 결과와 해당 inv_sqrt 레지스터를 :28469 `mul_57s_16s_72_1_1_U120`으로 전달한다.
3. U120 출력 grp_fu_6549_p2는 비트 추출·반올림·포화 선택을 거쳐 inv_sqrt_5(:53049) 또는 inv_sqrt_6(:53051)로 이어진다.
4. HLS RTL은 inv_sqrt_5와 mul_ln67_9를 :33065의 posedge 블록에서 stage0 조건으로 저장한다(:33175/:33192). mul_ln67_9의 입력 곱셈 U136(:28662)은 sext_ln67_reg와 **현재 조합 inv_sqrt_5_fu**를 입력으로 받는다. NR 다음 단계 연산을 만드는 실제 연결이다.
5. 마지막 inv_sqrt_6는 :63575→:53291→:28685의 Qx 곱셈으로 전달되고, :60035에서 반올림·포화한 결과를 :33023의 posedge 레지스터에 저장한다. 이것이 sin_theta 출력 쪽이다.

따라서 C++에 NR4가 있다는 이유만으로 네 번 반복 전체가 원래 한 클록 조합 연산이라고 설명할 수 없다. HLS는 실제 중간 레지스터를 생성했다. 스케줄 보고서도 inv_sqrt_4를ST4, inv_sqrt_5와 mul_ln67_9를ST5, inv_sqrt_6 및 Qx 곱셈을ST6에 배치한다. 해당 곱셈의 HLS 예상 지연은 대략3.14/3.56/3.96ns다.

## routed DSP를 확인한 결과

`path_analysis/dsp_registers.txt`는 routed DCP에서 직접 읽은 속성이다.

| 물리 연산기 | AREG | BREG | MREG | PREG |
|---|---:|---:|---:|---:|
| U118의 DSP2개 | 0 | 0 | 0 | 0 |
| U120의 DSP3개 | 0 | 0 | 0 | 0 |
| mul_ln67_9_reg_164408_reg | 2 | 0 | 1 | 0 |
| 마지막 Qx 곱셈 U138 | 0 | 2 | 0 | 0 |

특히 이름에 `reg`가 있는 mul_ln67_9_reg는 일반 FF가 아니라 DSP48E2로 매핑됐다. MREG=1이지만 BREG=0/PREG=0이고, 실제 최악 경로는 **B[bit]→B_ALU→ALU_OUT→P[bit]**를 지나므로 MREG를 통과하지 않는다. 레지스터가 존재한다는 것만으로 DSP의 모든 입력→출력 연결이 끊기는 것은 아니다.

타이밍 보고서에는 U118→U120→이 DSP의 B/ALU/P 경로가 비트별로 반복해 나타난다. 353단계와33개의 DSP_MULTIPLIER 타이밍 아크가 관측되지만, 독립 곱셈기33개를 소스 순서대로 수행한다는 뜻은 아니다. 시간 다중화한 연산기와 실제 DSP의 조합 경로가 결합된 긴 구조적 경로다.

## 확정할 수 있는 것과 남는 한계

- 확정: routed100경로는 FEx 공유 연산기군이며, 긴 경로는 합성 후 이미 존재한다. RTL 중간 레지스터와 물리 DSP의 비등록 통과 경로를 직접 확인했다.
- 해석: HLS의 연산별 시간 배치/추정과 Vivado의 공유·DSP 매핑을 거친 정적 타이밍 경로가 크게 달라진 사례다. 추가적인 순차 최적화·공유 제어의 상호배타 조건 등이 영향 줄 수 있다.
- 미확정: 해당 긴 경로 전체가 실제 동작에서 감응 가능한지, 특정 Vivado 변환 하나가 모든 차이를 유발했는지는 증명하지 않았다. 이를 이유로 false_path/multicycle을 추가하면 안 된다. 동일 RTL의 co-sim·합성 중간 netlist 비교·조건 경로 증명은 이번 범위에 포함하지 않았다.
- 이 결과만으로 DATAFLOW 자체가97ns 지연의 단일 원인이라고 단정하지 않는다. DATAFLOW 제거, 누산 포화 변경,18ns 스케줄링이 결합된 C16의 결과다.

현재는 15ns 목표에서 격차가 너무 크므로 이 구현을 미채택하고 보존하는 것이 합리적이다.
