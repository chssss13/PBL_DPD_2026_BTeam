# v2.3 이후 타이밍 개선을 위한 실험 기록

2026-11-02 기준.

v2.3에서 정확도와 II 조건을 충족했지만, 배치·배선 후 15 ns 타이밍 목표는 달성하지 못했다. 이후 비트 폭, 연산 구조, 구현 자원과 활성화 함수 방식을 바꾸며 개선 가능성을 검토했다. 이 문서는 각 시도의 근거와 결과, 채택하지 않은 이유를 정리한다. 새로운 최종 버전을 채택했다는 뜻은 아니다.

## 목표와 비교 기준

정확도와 HLS LOOP_T II=2를 유지하면서 Vivado 배치·배선 후 15 ns를 만족하는 것이 목표다.

- PA 정확도 필수 기준: NMSE ≤ -43.48 dB, ACPR L ≤ -50.39 dBc, R ≤ -47.83 dBc.
- EVM은 참고 지표다. 정확도 평가는 제공된 7,680샘플과 PA 모델 기준이다.
- 아래 배선 후 주기는 15 ns 제약과 WNS에서 환산한 값이다. 데이터 경로 지연 자체와 구별한다.
- HLS 자원은 추정치이고, 최종 자원은 Vivado routed 보고서 기준이다.

| 기준 설계 | PA NMSE | 배선 후 주기 | WNS |
|---|---:|---:|---:|
| 원본 sehyeon v1 | -43.57 | 17.506 ns | -2.506 ns |
| v2.3 | -45.11 | 18.105 ns | -3.105 ns |

v2.3은 정확도와 자원에 장점이 있었지만, 원본 v1보다 최종 타이밍이 느렸다. 그래서 v2.3의 뒷단을 개선하는 실험과 원본 v1에서 다시 출발하는 실험을 나누어 진행했다.

기준 자료: [v2.3 보고서](result/v2.3/README.md), [원본 v1 보관본](../result/07_lut_lookup/).

## 1. v2.3 뒷단을 먼저 확인

### z 정밀도 축소와 상태 갱신 병렬화

상태 갱신에 사용하는 z의 소수부를 10비트로 줄이는 경우와, 그 조건에 상태 갱신 병렬 계산을 추가하는 경우를 비교했다.

| 조건 | HLS 주기 | DSP | LUT | FF |
|---|---:|---:|---:|---:|
| v2.3 | 13.924 ns | 564 | 239,177 | 135,681 |
| z10만 | 13.924 ns | 564 | 239,917 | 135,736 |
| z10 + 병렬 계산 | 13.924 ns | 691 | 241,613 | 135,403 |

병렬 계산은 DSP를 127개 늘렸는데 최악 추정 주기가 개선되지 않았다. 후속 P&R 후보로 채택하지 않았다. 비트 축소만으로도 자원이나 타이밍이 반드시 좋아지지는 않는 사례였다.

근거: [z10 실험 폴더](result/post_v2.3/z10_csynth_comparison/).

### CE 제어 회로 단순화 진단

기존 v2.3 routed DCP 복사본에서 중복 CE 논리를 단순화하고 일부 신호만 재배선했다. 전체 WNS는 -3.105 → -3.087 ns로 약 0.018 ns만 개선됐다. 대상 CE 경로는 개선됐지만 같은 레지스터 뱅크의 데이터 입력 경로가 새 최악 경로가 됐다.

이는 C++ 변경이나 전체 P&R 재실험이 아니라 회로 진단용 ECO다. 전체 순차 등가성·co-sim을 검증한 최종 구현으로 취급하지 않는다. CE만 고쳐서는 주 데이터 경로 문제가 해결되지 않는다는 점을 확인했다.

근거: [CE 진단 기록](result/post_v2.3/ce_simplify_v23/README.md).

## 2. 원본 v1에서 정확도 여유를 확인

원본 v1의 직접 조회 LUT를 유지하면서 비트와 중간 계산을 바꾸는 방향을 먼저 확인했다.

| Python 후보 | NMSE | 판단 |
|---|---:|---|
| data15,3 / weight14,4, inverse16,6 등 축소 조건 | -43.01 | NMSE 미달 |
| 위 축소 조건 + inverse16,8 | -43.07 | NMSE 미달 |
| 축소 조건 + v2 방식 FEx | -43.09 | NMSE와 ACPR R 미달 |
| data16,3 복구, weight14,4·NR inverse16,8 | -43.32 | NMSE 미달 |

이 후보들은 단순히 data 한 항목만 바꾼 실험들이 아니다. 세부 설정은 각 실험의 스크립트와 settings.json을 기준으로 한다.

이후 원본 v1에서 weight15,4, GRU adder tree, recurrent 합산값17,4를 각각 또는 조합해 확인했다.

- weight15,4 포함 후보는 NMSE 약 -43.38~-43.39 dB로 미달했다.
- GRU adder tree만 적용한 출력은 원본과 같았다.
- recurrent 합산값17,4는 NMSE -43.57, ACPR -51.53/-48.65로 통과했다.
- tree + recurrent17,4 조합도 같은 정확도였으므로 C++·csynth 후보로 선택했다.

근거: [조합 실험 정확도](result/post_v2.3/accuracy/v1_factorial_accuracy/pa_comparison.txt), [비트 축소](result/post_v2.3/accuracy/v1_narrow_accuracy/pa_comparison.txt), [FEx 변경](result/post_v2.3/accuracy/v1_narrow_v2fex_accuracy/pa_comparison.txt), [data 복구](result/post_v2.3/accuracy/v1_data16_nr_accuracy/pa_comparison.txt).

## 3. v1 누산·곱셈 구현 변경

먼저 GRU tree + recurrent17,4를 적용하고, 곱셈을 DSP 대신 fabric으로 구현하는 조건을 추가했다. 여기서 fabric은 FPGA LUT 논리로 곱셈 회로를 구성한다는 뜻이며, 활성화 함수의 조회 표와 구별한다.

| 실험 폴더 이름 | 추가·유지 조건 | HLS 주기 | DSP | LUT |
|---|---|---:|---:|---:|
| v1_tree_rec17_csynth | tree + recurrent17,4 | 13.983 | 575 | 264,524 |
| v1_tree_rec17_fabric_csynth | 위 조건 + r 곱셈 fabric | 13.961 | 566 | 269,396 |
| v1_prelu_fabric_csynth | 위 조건 + PReLU fabric | 13.766 | 550 | 275,326 |
| v1_state_fabric_csynth | tree·rec17·r fabric + 상태 갱신 fabric | 13.961 | 551 | 269,099 |
| v1_prelu_state_fabric_csynth | PReLU·상태 갱신 모두 fabric | 13.842 | 535 | 274,961 |

주기 단위는 ns다. 각 실험은 C-sim 참조 일치와 LOOP_T II=2를 확인했다. 가장 좋은 HLS 주기를 보인 `v1_prelu_fabric_csynth`를 P&R까지 진행했지만, 결과는 **24.653 ns, WNS -9.653 ns**로 크게 나빠졌다. 최종 자원은 LUT 73,085 / FF 49,552 / DSP 549였다.

여러 변경이 누적된 조건이므로 PReLU 하나가 원인이라고 단정할 수 없었다. 이후 원본 v1에서 한 항목씩 바꾸는 방식으로 돌아왔다.

근거: [후속 실험 근거 목록](result/post_v2.3/README.md). 각 실험의 HLS 보고서와 보유한 설정·C-sim 비교 기록을 함께 보관했다.

## 4. 원본 v1에서 앞단·뒷단을 따로 변경

### PReLU만 fabric으로 변경

tree, recurrent17,4, r 곱셈 fabric을 모두 제외하고 원본에서 PReLU 곱셈만 변경했다. C-sim 출력은 원본과 일치했다.

- HLS: 13.936 ns, II=2.
- P&R: 18.672 ns, WNS -3.672 ns. 원본 17.506 ns보다 느렸다.
- 최종 자원: LUT 67,352 / FF 47,769 / DSP 570.
- 원본 대비 LUT +7,003, FF -471, DSP -14.

PReLU를 통과하는 경로만 별도 추출하자 해당 경로군의 최대 데이터 지연은 **17.486 → 16.835 ns**로 개선됐다. 다만 채널별로 개선과 악화가 섞였고, 다른 GRU 경로가 최악이 되어 전체 타이밍은 나빠졌다. 이 값은 PReLU 단독 연산 지연이 아니라 PReLU를 통과하는 레지스터 간 경로 지연이다.

판단: 앞단 개선 효과는 일부 확인했지만, 전체 타이밍과 자원 비용을 보면 기본안으로 채택하기 어렵다.

근거: [PReLU 단독 실험](result/post_v2.3/v1_original_prelu_only_csynth/), [PReLU 경로 비교](result/post_v2.3/prelu_path_reports/).

### 상태 갱신 곱셈만 fabric으로 변경

원본의 `n + z * (h_prev - n)` 식은 유지하고 곱셈의 구현 자원만 바꿨다. C-sim 출력은 원본과 일치했다.

| 항목 | 원본 v1 | 상태 갱신 변경 |
|---|---:|---:|
| HLS 주기 | 13.961 ns | 13.961 ns |
| LOOP_T II | 2 | 2 |
| DSP | 585 | 570 |
| LUT | 263,695 | 268,870 |
| FF | 142,769 | 142,769 |

최악 앞단 경로는 그대로였고, tanh → 상태 갱신 → 잔차 연결의 HLS 상태별 최대 지연은 12.658 → 13.520 ns로 증가했다. DSP 절약 효과는 있지만 타이밍 개선 근거는 없었다. 이 단독 조건의 P&R은 실행하지 않았다.

근거: [상태 갱신 단독 실험](result/post_v2.3/v1_original_state_only_csynth/).

## 5. 원본 v1에 선형 보간 적용

직접 조회 방식만 유지하려던 방향을 재검토했다. 원본 v1의 FEx와 GRU 계산 방식은 유지하면서 보간만 바꾸는 조건과, 보간에 비트 축소까지 적용하는 조건을 비교했다.

- 공통: sigmoid·tanh 각각 [-4,4) 256구간 선형 보간, accum18,3, reset2560.
- 원본 비트: data16,3 / weight16,4. 보간 표도 Q3.13에 맞춰 생성.
- 축소 비트: data15,3 / weight14,4. 보간 표는 Q3.12.
- FEx: 원본 NR 4회, inverse16,6 유지. data 타입으로 저장되는 중간값은 각 data 비트를 따른다.
- GRU: 원본 순차 누산, recurrent 합산값 별도 축소 없음, 원본 상태 갱신식 유지.
- PReLU·상태 갱신 fabric 변경은 포함하지 않았다. 보간 곱셈에는 fabric 구현을 사용했다.

| 조건 | NMSE | EVM | ACPR L | ACPR R |
|---|---:|---:|---:|---:|
| 원본 v1 | -43.57 | -47.70 | -51.26 | -48.02 |
| 보간만 | -45.37 | -49.30 | -53.50 | -50.28 |
| 비트 축소 + 보간 | -44.97 | -48.75 | -53.35 | -50.08 |

두 후보 모두 필수 정확도 기준을 통과했다. Python과 C++의 7,680샘플 출력은 해당 고정소수점 정수값 기준으로 일치했다.

| HLS 항목 | 보간만 | 비트 축소 + 보간 |
|---|---:|---:|
| 주기 | 13.961 ns | 13.844 ns |
| LOOP_T II | 2 | 2 |
| DSP | 585 | 575 |
| LUT | 233,030 | 234,523 |
| FF | 142,834 | 135,150 |

보간만 적용한 경우의 HLS 최악 경로는 입력 FC → PReLU → GRU 입력 곱셈이었다. 비트 축소까지 적용하면 tanh 입력 합산 → 보간 → 상태 갱신 → 잔차 덧셈 쪽으로 최악 경로가 이동했다.

근거: [보간만 csynth](result/post_v2.3/v1_interp_original_bits_csynth/), [비트 축소 + 보간](result/post_v2.3/v1_interp_narrow_bits_csynth/). [Python 정확도 비교](result/post_v2.3/accuracy/v1_interp_bit_comparison/pa_comparison.txt).

## 6. 비트 축소 + 보간의 P&R 결과

HLS에서 더 짧았던 비트 축소 버전을 P&R까지 진행했다. export_design 실행 시간은 31분 16초였고, 최종 경로 100개 보고서 생성도 완료됐다.

| 항목 | 원본 v1 | 이번 후보 |
|---|---:|---:|
| 배선 후 환산 주기 | 17.506 ns | 17.738 ns |
| WNS | -2.506 ns | -2.738 ns |
| 최종 LUT | 60,349 | 50,418 |
| 최종 FF | 48,240 | 42,091 |
| 최종 DSP | 584 | 320 |

정확도와 자원은 개선됐지만, 타이밍은 약 0.232 ns 나빠졌고 15 ns 목표는 미달했다. Hold 위반과 미배선은 없었다. 실행 시간이 짧아졌다는 것은 회로의 클록 주기가 짧아졌다는 뜻이 아니다.

### 최악 경로 분석

| 데이터 경로 지연 | 원본 v1 최악 경로 | 이번 최악 경로 |
|---|---:|---:|
| 논리 | 8.904 ns | 10.237 ns |
| 배선 | 8.582 ns | 7.482 ns |
| 합계 | 17.486 ns | 17.719 ns |
| 논리 단계 수 | 61 | 70 |

서로 다른 경로의 비교다. 보간 하나가 논리 지연 차이 전부를 만들었다고 해석하지 않는다.

이번 경로에서는 tanh 보간, 상태 갱신, GRU 곱셈·누산, r_h 관련 반올림·포화 논리가 연결되어 있다. 최악 경로는 DSP 곱셈 블록 3개를 통과한다. 상위 100개 중 tanh 보간 인스턴스 이름이 확인된 경로는 97개이며, 끝점은 r_h 관련 57개, r_pre 관련 38개, z_pre 관련 5개다. 슬랙 범위는 -2.738~-2.110 ns다.

RTL 자원 공유와 합성 후 논리 병합이 있으므로, 인스턴스 이름만으로 모든 계산이 같은 샘플의 알고리즘 순서대로 직렬 실행된다고 단정하지 않는다. 긴 연결이 데이터 의존성 때문인지, 공유 연산기·선택 회로 때문인지에 대한 추가 추적은 아직 끝내지 않았다.

근거: [최악 경로 100개](result/post_v2.3/v1_interp_narrow_bits_csynth/timing100/setup_paths100.rpt), [타이밍 요약](result/post_v2.3/v1_interp_narrow_bits_csynth/timing100/timing_summary.rpt), [자원 보고서](result/post_v2.3/v1_interp_narrow_bits_csynth/timing100/utilization.rpt).

## 현재 판단과 다음 확인

1. HLS 주기 개선만으로 P&R 후보의 우열을 확정하지 않는다. II·연산 매핑·자원은 HLS에서 확인하고 타이밍은 routed 결과로 판단한다.
2. 현재 v1 기반 보간 후보는 정확도·자원에 장점이 있지만 원본 v1의 타이밍을 넘지는 못했다. 보간만 적용한 원본 비트 후보의 P&R은 아직 하지 않았다.
3. v2.3과 이번 후보는 data·weight·accum 및 보간 구간 수는 같지만, GRU 누산 방식·recurrent 중간 양자화·FEx가 다르다. 같은 기능의 경로끼리 비교해야 원인을 좁힐 수 있다.
4. 다음 분석은 tanh 이후 긴 경로의 연산 공유, 선택 회로, 레지스터 경계를 확인하는 것이다. 코드 변경이나 새 합성 후보는 아직 결정하지 않았다.
5. 후속 실험 기록과 선별한 근거 보고서를 공유한다. 새 버전 번호를 부여하거나 실험 소스를 기본 구현에 반영한 것은 아니다. 전체 HLS 프로젝트·RTL·DCP·출력 벡터는 이 기록에 포함하지 않았다.
