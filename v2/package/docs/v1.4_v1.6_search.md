## v1.4 → v1.5 → v1.6 수정 과정

### 출발점: 정확도는 회복했지만 다음 샘플을 빨리 처리하지 못함

v1.3 후보 B에서는 GRU의 sigmoid와 tanh를 `double` 수학 함수로 계산했다.
정확도는 통과했지만, 이 함수들이 여러 클록에 걸쳐 계산되면서 시간 루프 II가 72가 됐다.
GRU는 이전 샘플의 은닉 상태를 다음 샘플에서 사용하므로, 아래 경로가 끝나야
다음 샘플의 해당 상태 계산을 진행할 수 있다.

```text
이전 은닉 상태 → 행렬곱 → sigmoid(r) → 후보 상태 계산 → tanh → 새 은닉 상태
                                                               ↓
                                                          다음 샘플에서 사용
```

여기서 II는 파이프라인 전체 길이가 아니라 다음 샘플의 처리를 시작하는 간격이다.
함수 하나가 매 클록 입력을 받을 수 있어도, 그 결과를 기다리는 재귀 경로가 길면
GRU 전체의 II는 커진다. v1.4~v1.6은 이 경로를 짧게 만드는 실험이었다.

### v1.4: sigmoid/tanh를 계산하는 대신 미리 만든 표에서 조회

`src/activations.h`의 활성화 계산을 LUT(lookup table, 값의 표)로 교체했다.
`tools/generate_activation_lut.py`가 Python에서 함수 값을 미리 계산하고,
`src/activation_lut.h`에 16비트 고정소수점 출력에 대응하는 정수로 저장한다.
FPGA에서는 exp나 tanh를 실행하지 않고 입력에 맞는 표의 값을 읽는다.
여기서 함수 값의 표라는 뜻의 LUT와 FPGA 자원 보고서의 LUT 수는 다른 개념이다.
이 표도 합성되면 논리 LUT나 메모리 등의 자원을 사용한다.

v1.4은 함수의 대칭성을 이용해 양수 구간 `[0,4]`만 1/512 간격의 2,049개 값으로 저장했다.
음수 입력은 절댓값으로 조회한 뒤 다음 식으로 출력을 복원한다.

```text
sigmoid(-x) = 1 - sigmoid(x)
tanh(-x)    = -tanh(x)

입력 → 절댓값 → 가까운 표 위치로 반올림 → 표 조회 → 음수이면 대칭 복원 → 출력
```

기존 double 계산을 정수 조회로 바꿔 II를 72에서 5로 줄였고,
C-sim PA 평가는 NMSE -43.65 dB, ACPR -51.86/-48.23 dBc로 통과했다.
다만 표의 격자 근사 때문에 정확도가 조금 떨어졌고, 절댓값·인덱스 계산·대칭 복원과
나머지 고정소수점 연산이 재귀 경로에 남아 II=2에는 도달하지 못했다.
II=5의 원인이 대칭 처리 하나뿐이라고 분리 측정한 것은 아니다.

### v1.5: 음수까지 저장해 입력 비트로 직접 조회

v1.5은 조회 경로를 단순하게 하려고 음수 구간도 표에 포함했다.
`<16,3>`의 입력 범위 `[-4,4)`를 1/512 폭의 4,096개 구간으로 나누고,
각 구간 중앙에서 계산한 함수 값을 저장한다.
표의 크기는 커지지만 절댓값 계산과 음수 출력 복원을 없앨 수 있다.

```text
16비트 입력 → 상위 12비트 [15:4] 추출 → 4,096개 표 중 하나 조회 → 16비트 출력
```

`<16,3>`은 소수부가 13비트이므로 하위 4비트를 인덱스에서 제외하면
입력 16단계, 즉 `16 / 8192 = 1/512` 폭을 하나의 구간으로 묶는다.
음수 비트 패턴에 맞게 표를 배치했으므로 실행 중 부호 변환도 필요 없다.
이 방식이 `ACT_LUT=2`이며, 활성화 함수 경계와 지연 제약도 함께 지정했다.
지연을 0으로 요청한 pragma가 있더라도 최종 지연은 합성 보고서로 확인해야 한다.

C-sim 정확도는 NMSE -43.67 dB, ACPR -51.82/-48.38 dBc로 통과했지만
전체 시간 루프 II는 여전히 5였다. 따라서 조회 방식을 바꾸는 것만으로는 충분하지 않았다.
합성 로그에는 상태 갱신 연산을 DSP의 3클록 지연으로 배치하는 동작도 나타났다.

### v1.6: 계산은 그대로 두고 연산을 클록에 배치하는 설정 변경

v1.6은 v1.5의 함수 값·비트 배분·가중치·초기화 조건을 그대로 사용한다.
새로운 수학 근사를 추가한 것이 아니라 HLS의 스케줄 설정을 다음과 같이 변경했다.

| 설정 | 변경 내용 | 목적과 주의점 |
|---|---|---|
| `DSP_FULL_REG=false` | DSP의 전체 레지스터화 기본 동작 해제 | DSP 연산을 자동으로 긴 레지스터 단계에 배치하는 동작을 줄일 여지를 줌. 모든 DSP가 조합회로가 된다는 뜻은 아님 |
| `CLOCK_UNCERTAINTY_NS=1.0` | 기본 여유 4.05 ns를 1 ns로 축소 | 15 ns 클록에서 HLS가 조합 경로에 쓸 수 있는 시간을 약 10.95 ns에서 14 ns로 늘림. 실제 물리 타이밍 여유는 줄어듦 |
| `TARGET_II=2` | 시간 루프 파이프라인에 II=2 요청 | 요청만으로 달성이 보장되지 않으므로 최종 보고서의 achieved II를 확인 |

이 변경들을 함께 적용한 결과 실제 합성 보고서에서 `LOOP_T II=2`를 얻었다.
각 설정이 단독으로 얼마만큼 기여했는지까지 분리한 실험은 아니므로,
특정 옵션 하나만으로 II=2가 됐다고 해석하면 안 된다.
진짜 은닉 상태 의존성을 무시하도록 지시하거나 서로 다른 시퀀스를 끼워 넣지는 않았다.

이후 전체 7,680샘플을 RTL co-sim으로 실행해 C와 일치하는지 확인했고 PASS했다.
RTL 출력의 PA 정확도도 v1.5과 같은 NMSE -43.67 dB, ACPR -51.82/-48.38 dBc였다.
즉, 계산 결과를 유지하면서 합성 스케줄을 바꿔 II를 5에서 2로 줄인 후보다.
다만 클록 여유를 줄였고 자원도 많이 사용하므로 실제 배치·배선 후 타이밍과 자원 수용 여부는 별도 검증 대상이다.

### 세 실험에서 유지한 것과 변경하지 않은 부분

입력·데이터 `<16,3>`, 가중치 `<16,4>`, 주요 누산기 `<32,12>`,
출력층 누산 `<16,3>`, 2,560샘플 초기화 조건은 v1.4~v1.6에서 동일하다.
FEx도 v1.3의 중간값 양자화 방식과 역수 `<16,8>`을 유지했다.
따라서 v1.4~v1.6은 FEx를 새로 바꾼 실험이 아니며,
FEx의 sqrt와 역수 내부에는 여전히 double 계산이 남아 있다.

정리하면 v1.4은 **활성화 계산을 표 조회로 교체**, v1.5은 **표 조회 경로 단순화**,
v1.6은 **동일한 계산의 합성 스케줄 조정**이다.
정확도는 각 후보의 출력으로, II는 HLS 합성 보고서로,
C와 RTL의 일치는 co-sim으로 각각 확인했다.

## v1.6 설정

- ACT_LUT=2: 4096-entry signed direct lookup, spacing 1/512, bin midpoint.
- LUT 저장값은 data_t의 raw integer. 입력 비트 [15:4]를 인덱스로 사용.
- FEX_INTERNAL_FIXED=1, FEX_INV_I=8.
- 2560샘플마다 reset, 64샘플 호출 사이에는 상태 유지.
- DSP_FULL_REG=false, CLOCK_UNCERTAINTY_NS=1.0, target clock 15 ns.
- TARGET_II=2 요청. 실제 보고서 LOOP_T achieved II=2, depth=37.
- 진짜 재귀 의존성을 false로 선언하지 않음, 시퀀스 interleaving 없음.

이 표의 LUT/타이밍은 HLS 추정값이다. 같은 후보의 실제 배치·배선 결과는 [v1.7 구현·PPA 문서](v1.7_implementation.md)에 기록한다.
기본 4.05 ns보다 clock uncertainty를 줄였으므로 물리 구현에서 timing closure가 필요.
이 단계에서는 정확도(C)와 II(HLS)를 확인했다. 이후 구현 결과 자원은 수용됐지만 15 ns 타이밍은 미달했다. 보드 실증은 수행하지 않았다.
로그의 'All loop constraints were NOT satisfied'는 남아 있음; 최상위 LOOP_T achieved=2를
보고서에서 직접 확인했으며 모든 하위 pragma 조건 충족을 의미하지는 않음.

## RTL co-sim

scripts/cosim_existing.tcl로 기존 합성 프로젝트를 초기화 없이 사용.
첫 시도는 C TB의 TV file 생성 단계에서 Error on TV file로 실패 (RTL 미실행).
포트별 TV 파일이 Windows 기본 stdio 한도를 넘을 가능성에 대응해 TB main에서
_setmaxstdio(2048)를 호출하도록 수정하고 재시도함. 결과는 cosim_retry.log 확인.

재시도 성공: 전체 7680샘플/120블록, C/RTL co-simulation PASS, 종료 코드 0.
Verilog co-sim top latency 166 cycles, top call interval 134 cycles.
이 top 호출 간격은 64샘플 단위의 제어 핸드셰이크를 포함하며 LOOP_T의 샘플 II=2와 구분한다.
RTL 출력 vs Python 참조 NMSE -196.93 dB, PASS.
RTL PA 평가 NMSE -43.67, EVM -47.64, ACPR L/R -51.82/-48.38.
세 정확도 기준 모두 통과. NMSE 여유는 약 0.19 dB로 작음.
평가 로그: results/v1.6_schedule/rtl_evaluation.txt, rtl_compare.txt.
co-sim 보고서 사본: results/v1.6_schedule/report/ResGRU_cosim.rpt.

현재 기본 ACT_LUT는 1이므로 성공 후보는 반드시 run_ii2_candidate.cmd의 ACT_LUT=2 및
스케줄 설정으로 재현한다. 단순 기본 명령은 같은 후보를 재현하지 않는다.
