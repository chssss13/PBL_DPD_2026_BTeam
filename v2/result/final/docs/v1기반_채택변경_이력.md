| 단계 | 당시 목표 | 변경 번호 |
|---|---|---|

```text
hyeonseo v1.7 → v2.1 → v2.2 → v2.3  [별도 계보]
```

## 2. v1 — 알려진 문제를 고치고 목표 조건 맞추기

### 1~4번의 출발점: v0의 알려진 문제

제공된 v0 알려진 문제는 활성화 함수(P1), 은닉 상태 유지(P2), 자료형의 표현 범위(P3), FEx 내부 계산(P4)이 학습 모델과 다르다고 설명했다. 이 문제들을 확인하고 하나씩 수정하는 것에서 출발했다.

#### 1. 은닉 상태 리셋 — P2

64샘플마다 은닉 상태를 초기화하면 golden의2,560샘플 구간 안에서 유지해야 할 기억이 끊어진다. 블록 크기는64로 두되, 구간 시작 블록의 첫 샘플에서만 상태를 초기화하도록 변경했다.

[변경 코드](../changes/코드변경.md#change-01)

#### 2. data·weight 표현 범위 확대 — P3

일부 값이 고정소수점 표현 범위를 넘어 포화되는 문제를 줄이려고 정수부를 늘렸다. 전체16비트는 유지하면서 data와 weight를16,2에서16,3으로 바꿨다. 이후에도 정확도 조건이 남아 있어 가중치 범위를5번에서 다시 살폈다.

[변경 코드](../changes/코드변경.md#change-02)

#### 3. 수식 기반 활성화에서 LUT로 — P1

학습 때 사용한 sigmoid/tanh와 v0의 hard 근사 함수가 달라서, 먼저 수식으로 직접 계산하도록 바꿨다. 하지만 합성에서 II가72까지 커지고 자원 부담도 높아졌다.

원본 `gru_cell.h`에는 LUT 함수인 `sigmoid_ele`·`tanh_ele` 호출이 주석 처리되어 있었다. 이를 보고 **미리 계산한 함숫값을 표에서 읽는 LUT 방식**을 선택했다. 표 크기와 인덱스 선택을 비교한 뒤4,096칸·인덱스 반올림을 사용했다. 당시 sigmoid 범위는−8~8, tanh는−4~4였다.

[변경 코드](../changes/코드변경.md#change-03) · 당시 LUT 검토 기록 · 원본 코드 확인: Git `f137df6`, `package/src/gru_cell.h`

#### 4. FEx 역제곱근의 범위와 정밀도 조정 — P4

FEx도 내부 계산값의 포화가 알려진 문제였다. 특히 입력 크기가 작으면 역제곱근 `inv_sqrt`가 커지므로, 이를 다른 중간값과 같은 `data_t`에 저장하는 부분을 먼저 살폈다.

처음에는 역제곱근을 별도의16,8 형식으로 저장해 범위를 넓혔다. 이후16,8→16,6으로 조정하면서 소수부를8→10비트로 늘려 정밀도를 보완했다. 즉 **처음에는 표현 범위 확대, 마지막 조정은 범위와 정밀도의 균형**을 위한 변경이었다. Newton–Raphson 반복은4회로 유지했다.

[변경 코드](../changes/코드변경.md#change-04) · FEx 실험 기록

### 5~8번: 남은 정확도·II·타이밍 조건 조정

#### 5. 가중치16,3→16,4 — 정확도 기준 통과

가중치494개 중1개가16,3 범위에서 포화되는 것을 확인했다. weight만16,4로 넓힌 Python 후보가 PA 정확도 기준을 통과해 C++에도 반영했다. 다른 가중치의 양자화도 함께 달라지므로 포화된 한 값만을 정확도 개선의 원인으로 단정하지는 않는다.

[변경 코드](../changes/코드변경.md#change-05)

#### 6. 현서 님의 HLS 설정 적용 — II 개선

정확도를 복구한 뒤에도 II가7이어서, 현서 님이 사용한 설정을 가져와 적용했다. 목표 클록15ns에서 uncertainty를4.05→1ns로 바꾸고, DSP full reg false와 LOOP_T II=2 요청을 적용했다. 그 결과 II가7→3으로 줄었다.

[설정 코드](../changes/코드변경.md#change-06)

#### 7. 상태 갱신식 정리 — 곱셈 두 번을 한 번으로

상태 갱신식의 곱셈을 줄이면 타이밍도 좋아지지 않을까 하는 생각에서 시작했다.

```text
이전: (1-z)·n + z·h_prev       [곱셈 두 번]
변경: n + z·(h_prev-n)         [곱셈 한 번]
```

식을 정리한 뒤 출력은 유지됐고 HLS DSP 추정 사용량은 줄었다. 다만 이 단계의 II는3으로 남았다.

[변경 코드](../changes/코드변경.md#change-07)

#### 8. BRAM 표 조회를 조합회로 조회로 — II=2 달성

기존 활성화 함수는 **BRAM에 저장된 LUT 표를 읽는 방식**이었다. 표를 읽는 지연이 포함된 구조에서 II가3에 머물러, 같은 함숫값을 조합회로로 조회하도록 바꿨다. 표를 전체 분할하고 조회 지연0을 요청한 뒤 LOOP_T II=2를 달성했다.

이 단계에서 v1의 정확도와 II 목표를 맞췄다. 이후 P&R에서는17.506ns로 측정되어15ns 타이밍을 줄이는 작업이 남았다.

[변경 코드](../changes/코드변경.md#change-08) · 변경 전 BRAM 조회 · 조합 조회 결과

**v1 완성 조건:** data16,3 / weight16,4 / accum18,3, 직접 LUT4,096칸, FEx NR4·inverse16,6. PA NMSE−43.57dB, ACPR 좌/우−51.26/−48.02dBc, II=2, P&R 비교 주기17.506ns.

## 3. v2 — 정확도 개선에서 경로 기반 최적화로

### 9. 선형 보간과 비트 축소 — 정확도와 자원 개선

직접 LUT 조회의 크기와 근사 오차를 함께 줄이기 위해 선형 보간을 적용했다. sigmoid·tanh를 각각256구간으로 나누고, 구간 시작값과 다음 경계점까지의 차이를 저장해 중간 함숫값을 계산했다. 보간 곱셈에는 FPGA의 일반 논리회로(LUT 등)를 사용했다. 여기서 논리 자원 LUT와 함숫값을 저장한 표는 서로 다른 의미다.

원본 비트 폭을 유지한 보간 후보를 먼저 평가한 뒤 data16,3→15,3, weight16,4→14,4로 줄인 후보를 선택했다. 이 결합 조건에서 **PA 정확도가 크게 개선됐다.**

| 지표 | 원본 v1 | 보간·비트 축소 후 | 개선량 |
|---|---:|---:|---:|
| NMSE | −43.57dB | −44.97dB | 1.40dB |
| ACPR L | −51.26dBc | −53.35dBc | 2.09dB |
| ACPR R | −48.02dBc | −50.08dBc | 2.06dB |

P&R LUT는60,349→50,418개, DSP는584→320개로 줄었다. 반면 비교 주기는17.506→17.738ns여서, 개선된 정확도·자원을 바탕으로 긴 경로를 줄이는 방향으로 넘어갔다.

### 10. 게이트별 곱셈 분리 — 긴 경로와 공유 연산기 검토

이 시점부터 타이밍 수치뿐 아니라 **어떤 연산과 선택 회로가 길게 연결되는지**를 분석했다. 일부 최악 경로10개만 보던 방식에서100개까지 기록하는 방향으로 넓혀, 반복되는 경로와 서로 다른 끝점을 함께 살폈다. 보관된100경로 보고서는9번 결과부터 확인되며, 이를10번 이후 개선 후보를 고르는 데 활용했다.

9번의 긴 경로에는 **tanh 보간→상태 갱신→GRU 행렬곱·누산→r_h 반올림·포화**가 이어졌다. 자원 공유에 따른 입력 선택이 이 연결을 길게 만드는지 살피면서, recurrent 곱셈을 r/z/n 게이트별로 나눠보는 방법을 선택했다.

`Recurrent_Gate_Product<GATE>`를 만들어 게이트마다 함수를 구분하고 DSP 곱셈의0클록 구현을 요청했다. P&R 비교 주기는17.738→17.524ns로 개선됐다. 이 단계까지를 **v2.4-S**로 보관했다.

### 11. 누산 폭 확대 — 반복되는 중간 포화 줄이기

게이트 분리 후에도 활성화·상태 갱신에서 GRU 연산과 자료형 변환으로 이어지는 경로가 길었다. 곱셈만 살피는 데서 더 나아가, **곱을 변환할 때와 누산값을 저장할 때 반복되는 반올림·포화 회로**를 줄일 수 있는지 검토했다.

좁은 누산기에서 포화만 빼면 큰 입력에서 값이 넘칠 수 있으므로, 중간 누산 범위도 함께 넓혔다. 선택한 방식은 GRU 입력·recurrent MVM의 누산기를18,3→21,6으로 바꾸고 마지막에18,3으로 변환하는 것이다.

```text
이전: 곱을18,3으로 변환 → 매번18,3에 누산
변경: 곱을18,3으로 변환 → 21,6에 누산 → 마지막18,3 변환
```

소수부15비트는 유지하고 정수부를 늘렸다. 18,3으로 제한된5개 곱의 합을21,6에서 받을 수 있어 중간 포화 부담을 줄일 수 있다. P&R 비교 주기는17.524→17.310ns, LUT는47,575→42,163개로 줄었다.

### 12. 입력 항별 곱셈 분리 — 공유 범위를 더 좁히기

누산을 넓힌 뒤에도 **tanh→상태 갱신→recurrent 연산→r_h 변환** 쪽 연결이 남았다. DSP를 조금 더 쓰더라도 연산 공유와 선택 회로를 줄이면 타이밍에 도움이 될 수 있다는 방향에서, 게이트별 분리를 더 세분화했다.

`Recurrent_Gate_Product<GATE>`를 `Recurrent_Term_Product<GATE,TERM>`으로 바꾸고 입력 항0~4를 각각 구분했다. 더하는 순서와 수치 형식은 그대로 두었다.

P&R 비교 주기는17.310→16.427ns로 개선됐다. DSP는333→337개로 소폭 늘었고 LUT는42,163→41,735개로 줄었다. 이후 경로 분석에서는 같은 항 안에서도 다른 사용처 사이의 공유가 남아 있음을 확인했다.

### 13. n 출력 행별 분리 — 남아 있는 n 곱셈 공유 개선

12번 결과를 RTL과 대조하니, 상태 갱신 결과가 **n recurrent 곱셈기로 들어간 뒤 누산과 r_h 변환까지 이어지는 경로**가 남아 있었다. 같은 입력 항이라도 직접 전달된 상태와 저장된 상태, 서로 다른 가중치를 선택해 같은 곱셈기를 쓰는 연결이 확인됐다.

따라서 n 쪽 곱셈의 사용처를 출력 행까지 구분해보았다. `Recurrent_Row_Product<ROW,TERM>`을 도입하고 출력 행0~4를 각각 호출했다.

P&R 비교 주기는16.427→15.266ns로 개선됐고 DSP는337→347개가 됐다. 변경 후 상위100개에서는 n 전용 곱셈기가 나타나지 않고 r/z 계열의 공유 곱셈이 남아, 이후 검토 대상을 옮겼다.

### 14. 상태 갱신용 z 폭 축소 — 값은 유지하고 곱셈 입력 줄이기

13번에서는 **tanh→상태 갱신→공유 z recurrent 곱셈→z_pre 변환**이 최악 경로였다. 추가 분리 후보들을 비교한 뒤,15.266ns 기준으로 돌아와 상태 갱신 곱셈 자체를 가볍게 만드는 방향을 검토했다.

sigmoid가 만드는 z는0~1 사이인데 상태식에서는 signed15,3으로 사용하고 있었다. 실제 표의 모든 입력을 검사하니 z의 Q12 raw 값이74~4022로 unsigned12 범위 안에 들었다. 그래서 상태 갱신에 넣는 z만 **unsigned12,0**으로 바꿨다. 소수부12비트는 그대로 유지했다.

P&R 비교 주기는15.266→15.146ns, setup 위반 끝점은143→53개로 줄었다. 이때 최악 경로의 끝점은 r_pre 변환으로 바뀌었다.

### 15. 상태 결과 포화 생략 — 최종15ns 조건 통과

14번 이후 남은 경로도 **활성화→상태 갱신→recurrent 연산**을 지났다. 이번에는 상태식을 계산한 뒤 결과를 저장하는 마지막 포화 선택을 줄일 수 있는지 살폈다.

상태식 `n+z·(h_prev-n)`은 `(1-z)·n+z·h_prev`와 같다. 0≤z<1이면 결과가 n과 h_prev 사이에 있으므로 같은 형식의 표현 범위를 넘지 않는다. 이 범위를 확인한 뒤 **15,3 형식과 반올림은 유지하고 상태 결과의 최종 포화만 생략**했다.

같은 형식의 AP_RND·AP_WRAP 중간값에 결과를 저장하고 그 비트를 h_next에 전달하도록 구현했다. GRU 곱과 누산 마지막의18,3 변환은 유지했다.

P&R 비교 주기는15.146→**14.907ns**, WNS는**+0.093ns**가 되어15ns 조건을 통과했다. C-sim 출력 일치와 HLS II=2도 확인해2026-11-03 현재 최종본으로 채택했다.
