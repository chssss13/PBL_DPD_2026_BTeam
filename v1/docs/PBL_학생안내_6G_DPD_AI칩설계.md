## 1. 배경 — 왜 이 과제인가

### 6G가 PA에 요구하는 것

- 6G는 sub-THz 대역, 수 GHz급 대역폭, 더 높은 차수의 변조를 지향합니다.
- 신호의 **PAPR(Peak-to-Average Power Ratio)이 올라가고**, 전력증폭기(PA)는 더 깊은 비선형 영역에서 동작하게 됩니다.
- PA의 **효율과 선형성은 서로 상충**합니다. 효율을 높이려고 포화 영역 가까이 쓰면 신호가 일그러집니다.

### 그래서 DPD가 필요합니다

PA가 신호를 일그러뜨릴 것을 미리 예측해, **반대로 일그러뜨린 신호를 입력**하는 기법입니다.
PA를 통과하고 나면 원래 신호로 돌아옵니다.

### 그런데 왜 전용 칩인가

- **DPD 연산량은 대역폭에 비례해 폭증**합니다.
- 기존처럼 DSP나 범용 FPGA에서 돌리면 전력 예산을 감당할 수 없습니다.
- → **저전력 전용 가속기**로 구현해야 합니다. 이것이 이 과제입니다.

### "6G인데 왜 200 MHz 데이터인가" ⚠️

반드시 짚고 갑니다.

우리가 쓰는 측정 데이터(`DPA_200MHz`, OpenDPD 공개 데이터)는 **디지털 PA에 200 MHz OFDM 신호**(20 MHz × 10 서브채널)를 넣고 측정한 것입니다.
6G 신호가 아닙니다. 이유는 단순합니다 — **현시점에 공개·검증된 광대역 PA 측정 데이터가 이 수준이 한계**이기 때문이고, 연구실 LW-ResGRU 논문도 이 데이터로 평가했습니다.

이 과제의 목표는 6G 신호를 처리하는 것이 아니라,

> **6G가 요구할 "광대역·저전력 DPD 가속기"의 설계 방법론을 확립하는 것**

입니다. 구체적으로는 *"대역폭이 N배가 되면 연산량·면적·전력이 어떻게 스케일하는가"* 를 정량적으로 답할 수 있어야 합니다.

## 2. DPD란 무엇인가 — 최소한의 배경

### 신호 표현

DPD가 다루는 것은 이미지가 아니라 **I/Q 시계열**입니다.

```
복소 baseband 신호  x(t) = I(t) + j·Q(t)
```

- 입력 텐서 형태: `(batch, frame_length, 2)` ← I와 Q 두 채널
- 출력도 동일: `(batch, frame_length, 2)`
- **분류가 아니라 회귀**입니다. softmax도 argmax도 없습니다.

### 학습은 2단계입니다 ⚠️

**DPD에는 직접적인 정답 라벨이 없습니다.** 이것이 DPD를 처음 접할 때 가장 헷갈리는 지점입니다.

```
[1단계] PA 거동 모델 학습
        x → [PA 모델] → y        정답 = 실제 측정된 PA 출력

[2단계] DPD 학습 (PA 모델을 고정하고)
        x → [DPD] → [PA 모델(고정)] → y'
        손실 = ‖y' − x‖          PA를 통과한 뒤 원신호가 되도록
```

2단계에서 gradient가 **고정된 PA 모델을 거쳐 DPD로 역전파**됩니다.

### 중요: PA 모델은 하드웨어로 만들지 않습니다

```
학습할 때:   x → [DPD 모델] → [PA 모델]  → y'     PA 모델 = 학습 도구
실제 배포:   x → [DPD 칩]   → [진짜 PA] → y      PA 모델은 사라짐
```

| | PA 모델 | DPD 모델 |
|---|---|---|
| 역할 | 학습용 대리 모델 | **실제 추론** |
| 하드웨어 구현 | ❌ | ✅ **이것만 칩으로** |

**여러분이 최적화할 대상은 DPD 모델 하나뿐입니다.**

## 3. 우리가 쓰는 모델 — LW-ResGRU

본 연구실에서 제안한 DPD 모델입니다.

| | 의미 |
|---|---|
| **LW** | Light-Weight — 경량 |
| **Res** | Residual — 잔차 연결 |
| **GRU** | Gated Recurrent Unit — 순환 셀 |

개략 구조:

```
I/Q 입력 → [FEx] → [잔차 연결된 경량 GRU 코어] → [FC] → I/Q 출력
```

### FEx(Feature Extraction)를 주목하세요

**FEx는 학습되는 레이어가 아니라 고정된 전처리**입니다. I/Q에서 비선형 피처 6개를 만듭니다.

```
[ I,  Q,  |x|,  |x|³,  sinθ = Q/|x|,  cosθ = I/|x| ]      |x| = √(I² + Q²)
```

- **weight가 없습니다** → 학습 대상이 아닙니다 (단, HW에서는 고정소수점으로 계산하므로 비트폭은 정해야 합니다)
- 대신 **제곱근과 나눗셈**(또는 1/√x)이 필요합니다 → 논문 HW는 Newton–Raphson으로 구현. LUT, CORDIC 등 다른 방법도 가능
- 이 블록이 **의외로 자원을 많이 먹습니다.** 최적화 1순위 후보입니다

> 정확한 블록 구성·수식은 **연구실 논문과 배포 패키지 코드**를 참조하세요.

### 여러분이 받는 것

1. **논문 HLS 설계 원본 (v0)** — 논문 Table III (5,3) 설정 그대로
2. **알려진 문제 목록** — v0을 학습 가중치로 돌렸을 때 정확도를 깎는 문제들의 **증상과 측정 손실** (해결 방법은 여러분 몫)
3. **학습된 float weight** (논문 모델, seed 4574)
4. **Golden reference** — PyTorch 출력, 테스트 입력, HLS와 같은 순서로 계산하는 Python 참조 모델
5. **검증·평가 도구** — PTQ(고정소수점) 시뮬레이션, PA 대리모델을 통한 NMSE/EVM/ACPR 계산, HLS 출력 비교(PASS/FAIL), 학습 가중치를 읽는 testbench

### v0 → v1 → 최종

| 단계 | 내용 | 규칙 |
|---|---|---|
| **v0** | 논문 HLS 원본 | 그대로 받음 |
| **v1 (기능 복구)** | 알려진 문제를 고쳐 §6의 **정확도 목표를 통과**한 버전 | `weight_t`, `data_t`는 **16비트 단어로 고정** (정수부·소수부 배분은 자유). 누산기 폭은 자유 |
| **최종** | v1을 최적화한 결과 | 비트폭 포함 모든 것이 자유. 단 정확도 목표는 항상 유지 |

**PPA 이력표의 0행은 v1입니다.** 개선률은 v1 대비로 계산합니다. (v0은 정확도가 나오지 않으므로 비교 기준이 될 수 없습니다.)

### 비트폭을 바꾸고 싶다면

1. **PTQ 시뮬레이션으로 먼저 손실을 재세요.** 재학습 없이 몇 분이면 비트폭별 ACPR 손실을 확인할 수 있습니다.
2. 손실이 허용 범위 안이면 그대로 HW에 적용합니다.
3. 손실이 너무 크면 **QAT 재학습을 조교에게 요청**합니다. 요청할 때 PTQ 측정 결과를 근거로 첨부하세요.

> 비트폭만 줄이고 검증하지 않으면 ACPR이 무너지는데, 이를 하드웨어 버그로 오해해 며칠을 낭비하는 경우가 많습니다. **반드시 PTQ 시뮬레이션 → HW 순서로** 진행하세요.

## 5. 반드시 알아야 할 전제 5가지

### ① 실시간 추론은 목표가 아닙니다 ⚠️

데이터 샘플링레이트는 **800 MHz**입니다. 보급형 FPGA에서 1 sample/clock 실시간 처리는 **불가능합니다.**

- 현실적 fabric fmax: 100~200 MHz 수준
- 8-lane 병렬로 쪼개면 lane당 100 MHz까지 내려오지만 하드웨어가 8배가 됩니다
- 참고로 논문 HW는 66 MHz에서 2 cycle마다 샘플 1개(33 MSps)를 처리합니다 → 실시간까지 약 24배

**→ 오프라인 검증으로 범위를 잡습니다.** 샘플을 메모리에 넣고 처리한 뒤 출력을 회수해 비교하는 방식입니다.

다만 다음은 **분석 과제**로 반드시 다루세요:

> *"실시간을 달성하려면 몇 배 병렬화가 필요하고, 그때 자원은 얼마인가?"*

이것이 6G 확장성 논의로 이어집니다.

### ② 지표는 정확도(%)가 아니라 dB입니다

분류 문제가 아니므로 "정확도 96%" 같은 표현은 쓰지 않습니다. **NMSE, ACPR, EVM** 을 dB로 보고합니다.

### ③ 양자화 노이즈에 매우 민감합니다

분류 문제에서 INT8은 거의 무손실이지만, **DPD는 다릅니다.**
ACPR은 스펙트럼 누설을 보는 지표라 양자화 노이즈가 곧바로 노이즈 플로어를 올립니다.

참고 실측치 (OpenDPDv2 논문):

| 조건 | ACPR | EVM |
|---|---|---|
| FP32 | −59.9 dBc | −42.1 dB (0.79%) |
| **W12A12** + 56% sparsity | **−51.8 dBc** | −35.2 dB |

**12비트에서도 8.1 dB를 잃었습니다.** "INT8이면 당연히 되겠지"로 접근하지 마세요.

### ④ 연산량 감소 ≠ 자원 감소 ≠ 시간 감소

- pruning으로 weight가 0이 되어도, **하드웨어가 같은 연산을 계속하면 처리시간은 그대로**입니다.
- MAC 수가 절반이어도 LUT가 절반이 되지는 않습니다 (제어 로직·메모리·라우팅 때문).
- **희소성을 실제 이득으로 바꾸는 회로**를 만드는 것이 여러분의 일입니다.

### ⑤ 기능 등가성이 최우선입니다

자원을 줄였는데 출력이 달라지면 **그 최적화는 실패**입니다.
모든 변경은 golden reference와 **bit-exact 또는 허용오차 내** 일치를 확인해야 합니다.

## 6. 평가 지표

### 선형화 성능 (기능이 유지되는지)

| 지표 | 의미 |
|---|---|
| **NMSE** (dB) | 모델 출력 정확도 |
| **ACPR** (dBc) | 인접 채널 누설. **실무에서 가장 중요** |
| **EVM** (dB / %) | 변조 품질 |

참고 기준점 (DPA_200MHz test set, PA 대리모델 통과, 제공 도구로 측정):

| | NMSE | EVM | ACPR L / R |
|---|---|---|---|
| DPD 없음 | −11.07 dB | −11.71 dB | −31.99 / −30.00 dBc |
| 논문 Table I — LW-ResGRU (H=5, L=3) | −43.48 dB | −46.65 dB | −50.39 / −47.83 dBc |
| 제공 모델 (seed 4574, float) | −45.52 dB | −49.42 dB | −53.59 / −50.43 dBc |

> 측정 방식: test set 7,680 샘플을 **2,560 샘플 구간 3개**로 나눠, 구간마다 은닉 상태를 0에서 시작하고 구간별 스펙트럼을 평균합니다 (OpenDPD 학습 로그와 같은 방식). 다른 방식으로 재면 숫자가 크게 달라지니, 반드시 제공 도구(`eval_pa.py`)로 재세요.

### 하드웨어 (PPA)

| 항목 | 측정 |
|---|---|
| **Area** | LUT / FF / DSP / BRAM |
| **Performance** | fmax, latency(cycle 및 µs), throughput |
| **Power** | 동적·정적 전력 (가능한 범위에서) |

### 목표

| 구분 | 목표 | 성격 |
|---|---|---|
| **정확도** (제공 모델, PA 통과) | NMSE ≤ **−43.48 dB**, ACPR ≤ **−50.39 / −47.83 dBc** (논문 Table I) | **필수**. 못 넘으면 그 설계는 무효 |
| **처리율** | **논문 주장 처리율: II = 2 @ 66 MHz (33.3 MSps)**, 구현 후 타이밍 통과 | **목표**. 논문 원본(v0)도 구현 후 16.66 ns(≈ 30 MSps)로 66 MHz를 통과하지 못했음. 달성 여부와 실제 처리율(MSps)을 반드시 보고 |
| **자원** | v0(논문 설계) 수준 이하. 조교 환경 참고값: **LUT 46,544 / FF 49,551 / DSP 648 / BRAM 0** (`ResGRU` 코어, Vivado 2024.1 구현 후). **팀 측정 환경에서 v0를 다시 구현한 값**을 기준으로 삼음 | **도전 목표**. 얼마나 가까이 갔는지로 평가 |

> 제공 모델(seed 4574)은 논문 평균보다 정확도가 좋습니다. 그 차이(NMSE 약 2 dB, ACPR 약 3 dB)가 **여러분이 근사·비트폭 축소 등에 쓸 수 있는 정확도 예산**입니다. 예산을 어디에 쓸지가 설계 판단입니다.
>
> 최종보고서의 핵심 그림: **"ACPR vs 자원" 평면에 v0, 논문(Table III), v1, 최종을 찍은 그래프.**

### 효율 (최종보고서 하이라이트)

- 파라미터당 ACPR 개선량
- **MAC 연산당 ACPR 개선량**

| **4** | 환경 구축 | 배포 패키지 받기, 툴체인 설치, **v0 합성 1회 성공**, golden·regression 환경 구축, v0을 학습 가중치로 돌려 알려진 문제 재현 | 빌드 성공 로그, v0 정확도 |
| **5** | **기능 복구 (v1)** | 알려진 문제 해결, PTQ로 16비트 정수부·소수부 배분 결정, **정확도 목표 PASS** | 📋 **월별보고서 ①** (v0 문제 분석 + v1) |
| **6** | **v1 측정·프로파일링** | v1 PPA 측정(PPA 이력표 0행), 임계 경로·자원 분포·latency 분해 분석 | **병목 우선순위 리스트** |
| **7-8** | 최적화 1차 | 저위험 변경 (pragma, 파라미터, 메모리 구조) | 변경별 PPA 이력 |
| **9** | 중간 점검 | 1차 결과 정리, 2차 계획 확정 | 📋 **월별보고서 ②** |
| **10-12** | 최적화 2차 | 구조 변경 (희소성, dataflow, 병렬도) | 주요 개선 |
| **13** | 합성·구현 | 최종 구성 합성, timing closure | 📋 **월별보고서 ③** |
| **14** | FPGA 실증 | 보드 동작, 실측 latency, 출력 회수·검증 | 실증 결과 |
| **15** | 종합 | 양 팀 비교, Pareto 분석, 6G 확장성 | 🎓 **최종보고서** |

### 4~6주차가 승부처입니다

여기서 **v1과 병목 리스트**를 만들지 못하면 이후 최적화가 전부 감으로 흘러갑니다.
v0의 문제를 고칠 때도 **측정으로 원인을 확인하고, 한 번에 하나씩** 고치세요. 4~6주차의 측정·분석이 이후 모든 판단의 근거가 됩니다.

**먼저 답해야 할 질문:**
- 임계 경로(critical path)는 어느 모듈인가?
- LUT / DSP / BRAM을 가장 많이 쓰는 모듈은?
- 전체 latency 중 각 단계가 차지하는 비율은?

### 규칙 2. 한 번에 하나만 바꾼다

두 가지를 동시에 바꾸면 어느 것이 효과였는지 알 수 없습니다.

**ACPR과 기능검증 열이 비어 있는 행은 무효**입니다.

### 규칙 4. Regression test를 먼저 만든다

## 10. 하드웨어 최적화 체크리스트

무엇을 시도할지 막막할 때 참고하세요. **순서는 프로파일링 결과가 정합니다.**

### A. 연산 구조
- [ ] PE 병렬도 조정 (늘리기 / 줄이기)
- [ ] MAC 시분할·공유
- [ ] **DSP ↔ LUT 자원 분배** (DSP48은 25×18 — 비트폭이 작으면 LUT가 유리할 수 있음)
- [ ] adder tree 균형화
- [ ] 곱셈 → shift-add 치환 (양자화가 Power-of-Two인 경우)
- [ ] FEx의 제곱근·세제곱을 LUT/CORDIC으로

### B. 메모리 / Dataflow
- [ ] weight 저장 위치: BRAM vs LUTRAM vs register
- [ ] weight stationary 등 재사용 전략
- [ ] line buffer / shift register
- [ ] full preload vs partial preload
- [ ] 메모리 뱅킹 / array partition

### C. 시간축 희소성 ⭐
LW-ResGRU는 GRU 기반이므로 **Delta 기법**(이전 상태와의 차이가 임계값 이하면 연산 생략)이 적용 가능합니다.
문헌상 **56% temporal sparsity**가 보고됩니다.

- [ ] delta threshold 기반 MAC 생략 회로
- [ ] zero 검출기 / 스케줄링 제어
- [ ] 생략된 연산이 **실제로 cycle·전력 절감으로 이어지는지 측정**

> ⚠️ **데이터 의존 분기는 HLS에서 pipeline을 깨뜨립니다.** variable II가 발생해
> 연산량을 줄였는데 처리시간은 그대로이거나 오히려 느려질 수 있습니다.
> 이 부분은 hand-RTL이 유리하며, **그 비교 자체가 좋은 보고서 내용**입니다.

### D. 제어 / 타이밍
- [ ] pipeline 단계 재분할, II 개선
- [ ] clock gating (동작하지 않는 블록의 클럭 차단)
- [ ] FSM 단순화
- [ ] retiming으로 임계 경로 단축

### E. HLS 특화
- [ ] `PIPELINE` / `UNROLL` / `ARRAY_PARTITION` / `DATAFLOW` pragma
- [ ] 고정소수점 타입 재설계 (`ap_fixed<W,I>`)
- [ ] 인터페이스 최적화 (AXI bundle)
- [ ] 합성 결과를 보고 pragma를 되돌리는 것도 최적화입니다

| HLS에서 데이터 의존 분기 | II 증가, 오히려 느려짐 | hand-RTL 검토 + 비교 기록 |
| Vivado 버전 불일치 | 팀원 간 결과가 다름 | 버전 통일, README에 명시 |
| 합성 리포트 미보관 | 재현 불가 | `results/<실험ID>/`에 바로 복사 |

- 배포 패키지를 받는 방법은 별도 공지합니다.

### 작업 환경 — Windows(내 PC) 또는 Linux(Ubuntu PC·Linux 서버)

두 방식 중 하나로 진행합니다. 설치·접속 방법은 배포 패키지의 `docs/작업환경_가이드.md`를 보세요. **연구실 서버 계정은 제공하지 않으므로** 각자 환경을 준비합니다.

| | A. 내 PC (Windows 10/11) | B. Linux (개인 Ubuntu PC / 쓸 수 있는 Linux 서버) |
|---|---|---|
| 툴 | Vitis HLS / Vivado 2024.1 **직접 설치** (디스크 50 GB+, 메모리 16 GB+ 권장) | 직접 설치 (서버에 이미 있으면 그대로), 같은 사양 권장 |
| 접속 | — | 서버라면 SSH (VS Code Remote-SSH 권장), 셸은 `bash`로 |

- **첫 주에 디바이스 xczu7ev로 구현(impl)까지 되는지 반드시 확인**하고, 안 되면 즉시 조교에게 알릴 것
- **PPA는 팀이 정한 하나의 측정 환경에서만** 잽니다. v0도 그 환경에서 다시 구현해 기준값으로 삼습니다. 최종 두 팀 비교는 조교가 같은 환경에서 다시 구현해 확인합니다.

## 부록: 용어집

| 용어 | 설명 |
|---|---|
| **DPD** | Digital Pre-Distortion. PA의 비선형성을 미리 보상하는 기법 |
| **PA** | Power Amplifier. 전력증폭기 |
| **I/Q** | 복소 baseband 신호의 실수부(In-phase)·허수부(Quadrature) |
| **PAPR** | Peak-to-Average Power Ratio. 신호의 첨두 대 평균 전력비 |
| **NMSE** | Normalized Mean Square Error. 정규화 평균제곱오차 |
| **ACPR** | Adjacent Channel Power Ratio. 인접 채널 누설 전력비 |
| **EVM** | Error Vector Magnitude. 변조 오차 크기 |
| **FEx** | Feature Extraction. I/Q에서 비선형 피처를 만드는 전처리 |
| **PPA** | Power, Performance, Area. 하드웨어 평가 3요소 |
| **II** | Initiation Interval. 파이프라인이 새 입력을 받는 간격 |
| **Temporal sparsity** | 시간축 희소성. 이전 상태와 차이가 작으면 연산을 생략 |
| **Golden reference** | 정확성 비교 기준이 되는 참조 구현 |
